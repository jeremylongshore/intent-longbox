056 §11 **R10**, verbatim in substance: `receiveCallback` refuses a domain another shop already holds (the security lens's **F8**) with a `SELECT` in the `connector-inbound` scope, and then introduces the token version **in a separate transaction** under the shop's own tenant context. The gap between them is small — no network call falls inside it — but it is a real time-of-check-to-time-of-use window, and the failure it admits is the one F8 exists to prevent: **two shops holding live tokens for one store, so that an `app/uninstalled` ends the wrong shop's authority** (053 §7.3).

R10 examined two fixes and rejected both, and this record does not reopen either:

- **(a) Move the check inside the transaction.** It cannot go there and stay correct. That transaction runs under a TENANT context, under which `connector_token_version` rows belonging to other shops are invisible, so the check would return zero rows every time and **fail open** — 056 §6.1's exact trap one layer over.
- **(b) Run the whole install in the `connector-inbound` scope.** That needs a `service_write` policy on `connector_token_version`, and widening a write policy to close a race is the move the security lens's **F1** punished.

R10 then named the fix this bead executes: *"a serialization point the database already owns"* — `shop.shopify_domain` carries a unique index and the install does not write it.

**Two facts that made it safe to do nothing until now, both REPRODUCED at `f957aa3` and unchanged at `eed115f`:**

1. `shop_shopify_domain_is_one_store` exists — `migrations/026:387`, `UNIQUE (shopify_domain) WHERE shopify_domain IS NOT NULL`.

## 3. Decision A — the install CLAIMS the store, and the `23505` is where the rule is guaranteed

**Inside the transaction that introduces the token version, under the tenant context of the shop the install state named, the callback writes `shop.shopify_domain` for that shop.** It is the FIRST statement of that transaction. `claimStoreDomain` is module-private in `src/services/connectors/shopify/api.ts`, on `retireEveryLiveTokenForDomain`'s precedent: it is correct only there, and reached from anywhere else it is an unguarded write to another tenant's configuration.

### 3.1 Why a unique index is the right instrument, and it is the same property 056 §6.3 called a defect

**A unique index is checked with row-level security OFF, against every row in the table, including rows the caller cannot read.** 056 §6.3 recorded that as an oracle. It is also exactly what a cross-tenant uniqueness rule needs: the tenant context that makes fix (a) fail open is the same context the index does not consult. Two concurrent callbacks for one store become **one winner and one `23505`**, decided by the database under no isolation assumption at all (041 §4.2(i): *"a constraint is the cheapest correct answer and it is correct under every isolation level"*).

**The row lock is not the mechanism and saying so matters.** Two shops are two `shop` rows, so their row locks never conflict; what serialises them is the btree unique waiting on the other transaction's uncommitted index entry. A future reader who "optimises" this into a `SELECT … FOR UPDATE` on the shop row would remove the guarantee and keep the appearance of one.

### 3.2 The row count is the authorization (056 §6.2)

`UPDATE shop SET shopify_domain = $1 WHERE id = $2` is followed by a check that exactly one row was affected, and a zero is a refusal. **An `UPDATE` that matches no row SUCCEEDS**, so without that check a wrong shop id — or a future change to the context this runs under — would write nothing, raise nothing and let the install proceed unclaimed. 056 §6.2 states the rule; this is it applied rather than restated.

### 3.3 What the merchant sees, and what they do not

**One code reaches the wire, and it is the code that already reached it.** `src/routes/connectors.ts` maps every `CallbackRefusal` but `rate_limited` to `CONNECTOR_CALLBACK_REFUSED` with empty `details` — pinned by `tests/integration/connector-http.test.ts` — so a merchant completing OAuth for a store another Longbox shop holds is answered **identical in bytes** to one presenting an unknown state, an expired state or a forged signature. **The word is narrowed from v1.0.0's "byte-identically", which over-claimed by one dimension:** the pre-exchange refusals (bad signature, unknown state) and the post-exchange ones (scope, claim) differ by ONE OUTBOUND CALL to Shopify's token endpoint, which is observable to anyone who can watch this server's egress. That distinction is **unreachable without a valid HMAC** — a caller who cannot sign cannot get past step 3 — so it discloses nothing to the population the constant answer exists to defend against, and it is stated rather than papered over. The `23505` is mapped to the SAME internal member the F8 fast path raises (`domain_claimed`), for a reason worth stating: a caller must not be able to tell a store claimed a second ago from one claimed a month ago.

**Byte-identity with a NEVER-INSTALLED store is impossible and the record says so rather than implying it.** A never-installed store's callback **succeeds**; a claimed store's is refused. Two different outcomes cannot be made identical without refusing every install. So the reachable target — identity with every other refusal — is the one that was taken, and the residual is §9 R1.

**The shop-facing sentence is in `pnpm connector-install`'s output, not in the response**, and what SHIPPED is three clauses: *a store belongs to at most one Longbox shop; completing this install records this store on this shop; if this store is already recorded against a different shop the callback is refused and nothing is written, and moving a store between shops is an owner decision somebody makes deliberately.*

> **A FOURTH CLAUSE WAS DRAFTED AND IS DROPPED (v1.0.1, the gate audit's S2).** It read *"the claim is what makes two shops holding one store impossible rather than merely unlikely — the database decides it"*. **021 B16 makes any statement about what the software CANNOT do a COMMITMENT at whatever class the reader is in, not a description**, and that sentence would be read as a guarantee against an attacker rather than against a race — which is neither what §3 argues nor what §9 R4 leaves standing (056 R1 is unchanged: a compromised process can claim any unclaimed store). The mechanism belongs in this record and in the code comments, where a reader can check it; the CLI says what HAPPENS. The comment above the block in `scripts/connector-install.ts` records the removal and its reason, so the clause is not re-added by somebody who thinks it reads better.

**It is routed to 021 T26 pre-send** before it appears in any merchant-facing surface — the CLI is read by an owner or by us, and the merchant-facing landing is still `pending: true` with E10-B02 named (053 §7.2). The one-shop sentence and its bounds are registered in **021 §4a** as **`C-CANDIDATE-E03D22-1`**, owned by E10-B02 and filed BESIDE `C-CANDIDATE-E03B06-1` rather than inside its constraints cell (021 → v1.5.1, no existing row's text changed) — so the copy has a home, and its prohibition, before it has an audience.

### 3.5 The MINT refuses too, so the merchant does not spend a code to be told (F6)

`mintInstallState` now runs one `SELECT` before it writes the state: *does another shop already hold this store?* If so it refuses, writes no state row, and `pnpm connector-install` prints the refusal instead of an authorize URL.

**It is an EARLY REFUSAL AND NOT A CONTROL, and the distinction is the whole reason it is safe to add.** The claim in §3 is the guarantee. Without this, an owner is sent to Shopify, approves a consent screen, and the callback refuses **after** the authorization code has been exchanged — a single-use code spent to learn something this system already knew when the CLI was run.

**It may live here and NOT in `completeInstall` for one specific reason.** This act runs on the SCHEMA OWNER's connection (`pnpm connector-install` uses `resolveMigrateUrl`), which sees every shop's row — and for the schema owner the index was never an oracle anyway, because the owner can read those rows directly (056 §6.3). Put the same `SELECT` inside the callback's transaction and it runs under a TENANT context, sees nothing, and **fails open** — 056 §6.1 exactly. A caller who somehow reached `mintInstallState` with a tenant context is refused nothing here, which is correct: this check is allowed to be silently unhelpful, never silently wrong.

**It refuses `id <> $2`, not "this domain exists"** — a shop re-minting for the store it already holds is the ordinary re-install and must keep working.

### 3.6 The SIBLING unique violation is a refusal, not a 500 (F8)

`connector_install_state_use`'s `UNIQUE (state_id)` is what 053 §5.2 calls *"the whole mechanism"* for a replayed callback, and it is raised **inside** `completeInstall`'s transaction — where nothing caught it. So the one refusal the schema is proudest of arrived as an unhandled `23505`: a 500 with a stack, on a route where every other refusal is one 4xx code. It is now mapped to **`state_replayed`**, the same member the pre-transaction read raises for the same fact, so the two paths cannot disagree.

> **WHY IT HAD SURVIVED, WHICH IS THE USEFUL PART.** A *sequential* replay never reaches the constraint: the state read's `LEFT JOIN connector_install_state_use` sets `spent`, and the refusal happens one step earlier without opening a transaction. Only a RACE passes that read twice. **The existing test's comment claimed it "dies on the constraint" and it did not** — and its assertion was `.rejects.toThrow()`, which would have accepted the 500 as a pass. Both are repaired, and a new case races two callbacks over one state to reach the constraint for real; removing the mapping fails that case and nothing else, which is how the path is known to be reached.

### 3.4 Two behaviours that follow, argued rather than inherited

- **A shop that MOVED store is re-pointed, not refused.** The owner asked for the new store at mint time and the callback proved the same domain against the state twice (053 §8.1). Refusing would strand a shop on a store it no longer sells into.
  - **The re-point RELEASES the abandoned store's claim while that store's token may still be live, and the reviewer chased where that leads: nowhere bad** *(v1.1.1)*. The column holds one value, so claiming X clears Y. A rival shop cannot then take Y, because the **F8 fast path refuses an install for a store another shop holds a LIVE token for** — and the abandoned token is still live until it is retired or uninstalled. So the window between a re-point and a retirement is one in which Y is claimed by nobody and installable by nobody, which is a gap in tidiness rather than in safety: **there is no state in which two shops hold one store.** The claim and the token liveness are two different facts and the pair of checks covers the cross product; if they are ever unified, this is the case to re-derive.
- **The same shop may claim the same store repeatedly.** The claim is an `UPDATE` of that shop's own row, so a rotation — which 050 §2 Q2 permits to leave two live versions — writes the same value and conflicts with nothing.

**One consequence outside this bead's frame, recorded because it is a real behaviour change:** `src/consumers/index.ts:124` reads `shop.shopify_domain` and falls back to `SHOPIFY_STORE_DOMAIN`. For a connector-installed shop that column is now populated, so the draft consumer's store domain becomes the store the GRANT names instead of a deployment-wide environment variable. That is the correct direction — it agrees with the client resolution 053 §7.4 already performs — and it is stated here so it is not discovered as a surprise.

## 4. Decision B — an uninstall does **NOT** release the claim

**This is the one place this record decides something 056 did not, and it was drafted both ways.**

**The release version was abandoned on a mechanism before it was judged on merit.** `receiveWebhook` runs its whole transaction in the `connector-inbound` service scope — it must, because a webhook that matches no install writes a receipt with a NULL `shop_id` (053 §5.5) and a NULL matches no tenant policy. `shop` has **no `service_write`** in that scope (`src/db/rowLevelSecurity.ts`: *"Nothing writes it inside a scope — creating a shop is a schema-owner act"*), so a NULL write from inside that transaction is refused by the policy. Adding one would be F1's widening in the same shape R10 rejected, to close a smaller problem. Releasing in a second transaction after the commit is expressible but introduces a half-state — retired tokens, standing claim — on exactly the crash R10's own construction exists to make unrepresentable.

**And on merit the answer is the same, which is why this is a decision and not a workaround.** `shop.shopify_domain` is CONFIGURATION under 034 §4.2 — it says **which store this Longbox shop sells into**. An `app/uninstalled` is a third party's act at another system. Releasing on it would mean a merchant removing the app during a theme migration silently un-configures their Longbox shop and opens their store to being claimed by a *different* Longbox shop. **A control that a third party can trigger to widen who may claim a store is worse than the one it replaces.**

**What `connector_token_version.shop_domain` means afterwards is unchanged, and the split is 034 §4.2's own.** That column is a FACT about a past grant — which store this token was granted for — and it is append-only. The claim on `shop` is a STATEMENT ABOUT THE PRESENT and is corrected in place. The uninstall path continues to resolve its tenant from the append-only column and **never** from the claim, which is the 053 §5.5 finding-1 fix and stays true; `tests/integration/connector-oauth.test.ts` now proves the independence on a shop where the two disagree (a token version introduced with no install, so no claim exists at all — 053 §5.3's Dev Dashboard shape) rather than by asserting a NULL that this bead makes false.

**The cost is stated and owned:** moving a store to a *different* Longbox shop needs a schema-owner act today. That belongs to the bead that owns **winding a shop down**, not to a webhook handler — **`longbox-e5b.16.1`** (alias of record **E17-B01**; see §9 R2 on why this record leads with the id), with **E03-B09** `longbox-e5b.3.9` owning the retention and deletion policy the release has to satisfy. §9 R2 carries it. *(v1.0.1: v1.0.0 said "offboarding (E15)", which is wrong — `longbox-e5b.15` is CI/CD and controlled release and owns none of this. Named by the gate audit.)*

## 5. Decision C — the claim is the FIFTH position in 042 §5.3(b)'s order, and the SIXTH added to it

**`request_idempotency` INSERT → `app_session` (`FOR NO KEY UPDATE`) → `user_credential` (`FOR UPDATE`) → `user_authenticator` (`FOR UPDATE`) → `shop` (the store claim) → `scan_session` anchor (`FOR UPDATE`).**

> **ONE FRAMING, IN ALL THREE PLACES** *(v1.1.1, the invariant review, which found this record's heading, its body and `scripts/architectureRules.ts` each counting differently)*: the store claim is **the FIFTH position in the ORDER and the SIXTH ADDED to it**. Both halves are true and neither alone is unambiguous — 042's change-log idiom counts positions the order HAS (a fourth at E03-D06, a fifth at E03-D11, a sixth here), while the lint's comments number by SEQUENCE. The record, the RTM and the rule now use the same sentence.

- **After the three identity positions**, because the authentication hook takes `app_session` before any handler body exists and the privileged sign-in takes both credential locks while establishing the session a shop-config write would run under. This is the lint pinning the order the code already has, exactly as the credential positions were.
- **Before the `scan_session` anchor**, coarse before fine, and the hierarchy is real: a `scan_session` belongs to a shop. A handler that held a session anchor and then reached for the tenant row would deadlock against one doing the reverse — and the reverse is what the install callback does.

**No chunk in the tree takes two of the six today**: a provider callback carries no `Idempotency-Key`, no cookie and no scan session. The position is registered now, while the answer is free, for the reason the authenticator position was — so the handler written six months from now inherits an order instead of choosing one. It is enforced by `pnpm arch`'s `fixed-lock-order` rule and carries **four** fixtures — one positive and **three** negative — because a rule that has never failed on its own new pair is indistinguishable from one that cannot. *(v1.1.2: v1.1.0 said three; the fourth is v1.1.1's shape fixture, added with the regex and not counted with it.)*

**WHAT THE NEW LOCK COSTS THE COUNTER: NOTHING MEASURABLE, and that is a probe rather than a hope (the security lens's F9).** Every foreign key INTO `shop` takes `FOR KEY SHARE` on that row, so the obvious worry is that an install in flight stalls the shop it belongs to. It does not, and the reason is mechanical: `UPDATE shop SET shopify_domain` touches no key column, so PostgreSQL takes **`FOR NO KEY UPDATE`**, which does not conflict with `FOR KEY SHARE`. Probed while a claim was held uncommitted on its own connection — a `SELECT` of that shop and an `INSERT` of a `scan_session` at that shop both completed, neither blocked — and pinned as a case rather than left as an argument.

> **ONE OBSERVATION IS MARKED AS INFERRED RATHER THAN ESTABLISHED.** The raw `23505` from the claim carried **no `detail` field** in the observed run, which would mean the refusal discloses even less than §3.3 requires. **It is recorded as OBSERVED ONCE with the mechanism INFERRED** — most likely 029's policy leaving the app role unable to read the conflicting row, the same belt-and-braces 056's R7 amendment describes on a different constraint — and **no artifact may state it as a property until it is re-verified as the SCHEMA OWNER**, where the absence would mean something different. Nothing in this record depends on it: §3.3's guarantee is the wire envelope, which carries no `detail` in any case.

## 6. What happens to 056 §6.3 — restated, **not** discharged

**R10 is DISCHARGED. §6.3 is NOT, and the honest statement is that its stated reason for being latent is now FALSE.**

§6.3 said: *"there is nothing to repair today and something to repair before a route ever sets a domain."* This bead is a route setting a domain. So the oracle is **REACHABLE**, and the record must say what bounds it instead.

**What bounds it: the value stops being freely choosable at the moment it becomes writable.** §6.3's rule — *a UNIQUE over a client-choosable value must be prefixed by the tenant* — has exactly one discharge route in that section, and this index cannot take it: **the constraint's entire purpose is cross-tenant uniqueness**, so prefixing it with `shop_id` would make it assert nothing. This record therefore argues a **SECOND discharge route for the rule, and offers it as a general one**:

> **A UNIQUE over a client-choosable value must either be prefixed by the tenant, OR the value must stop being freely choosable at that scope — by requiring the caller to prove control of it, where the proof is PER-PROBE and NON-REPLAYABLE and the value is one the caller ADMINISTERS.**

**The two qualifiers are load-bearing and v1.1.0 left them implicit** *(v1.1.1, the invariant review)*. Without **per-probe and non-replayable**, one proof would unlock many questions and the route becomes a scanner at the cost of a single grant — here every probe needs a FRESH `connector_install_state` row and a REAL grant at the store being asked about, and a spent state cannot be re-presented (053 §5.2). Without **administers**, the bit learned would be about a third party rather than about the asker, which is precisely §6.3's objection and not a discharge of it. A future application of this rule that drops either qualifier is not this rule.

⚠ **THE RULE IS PROSE-ENFORCED TODAY. There is no lint.** Nothing fails a build when somebody adds a `UNIQUE` over a client-choosable column on a policied table, and nothing checks that a new writer of such a column proves control first. `pnpm arch` polices the lock order, the writer inventories and the module graph; it does not police this. The next reader who wants it mechanical is looking at a schema-walk over `pg_index` cross-referenced with the policied set — real, and not built here.

Here the proof is a completed OAuth grant: to reach the claim a caller must hold real merchant consent at the store they are asking about, minted through an install state an owner asked this system for, with the state's own domain matched against the callback's twice. **So the one bit learnable is *"is MY store already a Longbox customer"*, about a store the caller administers — not a probe over stores at large, and not commercial information about third parties, which is what §6.3 objected to.** The route cannot be turned into a scanner: every probe costs a fresh state row and a real grant at the store being probed.

**What is NOT claimed.** The index is still not tenant-prefixed and a `23505` is still distinguishable from an `UPDATE 1` to anyone who can execute both. Nothing here makes that untrue; what changes is who can execute them and about what. 056 §6.3 keeps its rule and gains an amendment row naming this exception and its bound.

## 9. Residual risk

**R1. A merchant who completes a grant learns whether their own store is already a Longbox customer.** §6's bound, stated as a residual rather than as a closed item: success and refusal are different outcomes and cannot be made identical without refusing every install. It is one bit, about a store the caller administers, at the cost of a real OAuth grant per probe. **No artifact may describe the callback's refusals as indistinguishable from a successful install.**

> **ITS DISPOSITION AGAINST 019 T24 IS STATED BY NAME, AND NO WAIVER IS SOUGHT** (v1.0.1, the gate audit's S4). **T24 is NON-WAIVABLE**, so a residual sitting anywhere near it must say which side of the line it is on rather than leaving a reader to decide.
>
> **T24's instrument measures ROWS that cross tenants** — 056 §1 E11 / I16's `pnpm audit:cross-tenant` derives its edges from the catalog and counts rows whose `shop_id` disagrees with the parent they point at, and 056 R4 states plainly that it detects internally inconsistent rows and never a read. **A `23505` crosses no row.** The refusing transaction rolls back whole: no claim, no `connector_token_version`, no `connector_install_state_use`, and the audit's count is unchanged in both directions. Nothing is read across a tenant either — the statement is an `UPDATE` of the caller's OWN row under its own context, and the index is consulted by PostgreSQL rather than by the caller.
>
> **So this is NOT a T24 event and no waiver is sought or implied.** What it is instead is the class 056 §6.3 named — a distinguishable outcome over a value another tenant holds — and that class has never been inside T24's definition; §6 is where it is bounded and this residual is where it is carried. **Two things follow that no artifact may soften.** The bound is the COST of a probe (a completed OAuth grant at the store being asked about), not the absence of one. And if a future change ever lets this refusal be reached WITHOUT proving control of the store, §6's second discharge route stops applying and the disposition above stops being true — that is the re-open trigger, and it is written here rather than assumed.

**R2. Moving a store to a DIFFERENT Longbox shop needs a Longbox code change, and the cost falls on the MERCHANT as well as on us.** §4's cost, stated from both ends because v1.0.0 stated only ours (the security lens's F5).

**The merchant's bound is the sharper one and was missing:** a shop that stops using Longbox holds that store's claim **forever**, so a merchant who wants to move to another Longbox shop — a new owner, a new account, a franchise reorganisation — is gated on Longbox staff acting. That is a real cost and it is chosen deliberately, because the alternative is worse in the direction that matters: releasing on uninstall lets a third party's act at Shopify un-configure a shop (§4), and the store **cannot be squatted** in the meantime, since taking a claim costs a completed OAuth grant at that store.

**And the recovery sentence in v1.0.0 was wrong.** It said *"the recovery is an `UPDATE` by the schema owner"*. It is not a PRIVILEGE problem: the app role holds full DML on `shop` and a shop **can clear its own claim** under its own tenant context. What is missing is a **CODE PATH** — no route, no CLI, and no fact recorded when a claim is released. So E17-B01 owes a path and a record, not an escalation. It becomes a real workflow when winding a shop down does, and the owners are **`longbox-e5b.16.1`** (*self-service organization, shop and location onboarding, import and offboarding/export*) with **E03-B09** `longbox-e5b.3.9` for the retention and deletion policy it must satisfy

> **THE BEAD IS NAMED BY ID BECAUSE ITS TWO REVIEWERS GAVE IT TWO ALIASES** *(v1.1.1)*. The gate audit called `longbox-e5b.16.1` **E17-B01**; the invariant review called it **E16-B01**. **The id is the same in both**, so the work is unambiguous and nothing here turns on the label. The bead's OWN record settles it — its description reads *"Alias: E17-B01 under LBOX-E17"* and its metadata carries `lbox.alias: E17-B01`, consistent with CLAUDE.md's graph (E16 is `longbox-adk`, reused; E17–E19 are `longbox-e5b.16`–`.18`) — so **E17-B01** is the alias of record and E16-B01 is a slip. This record leads with the id in every carrier for exactly that reason: an id resolves, an alias is what two careful readers disagreed about on the same day. — beside 056 R8's undrained-outbox question, which is the same shape and the same pair. *(v1.0.1 correction: v1.0.0 named "E15", which is CI/CD and controlled release and owns none of this.)*

> **A -D BEAD IS PROPOSED AND NOT CREATED, deliberately.** **E03-D30** — *"Release a store's domain claim when a shop is wound down, as a fact rather than a silent NULL"* — would take **`longbox-e5b.3.40`** (`.3.39` is E03-D17's own proposed D29 and is not created either, so neither id is claimed by this record). A builder does not file beads into another bead's subtree mid-flight; the session creates it, or folds it into E17-B01's acceptance, after this bead closes. **If it is created, its first constraint is that a release must be a FACT and not an `UPDATE` to NULL** — the reason §4 gives for not releasing on a webhook is that a claim disappearing with no record of who released it and why is the same defect one level up.

**R3. The F8 fast path can still be raced, and it is now allowed to be.** It reads outside the transaction and is no longer the guarantee; when a racing INSTALL passes it, the claim refuses that install. *(v1.1.0: v1.0.0 said "when it is raced, the claim refuses", full stop, which reads as a claim about every way a token can appear. It is not — see R5.)* What survives is that the common case is refused **before** the authorization code is exchanged. A merchant who loses the race has spent a code and must be sent back through — the state itself is unspent (053 §5.2's H4), so the install can be restarted without a new state.

**R4. This bead does not change what a compromised process can do.** 056 R1 is unchanged: the application role can set the tenant context to any value it likes, so a compromised process can claim any unclaimed store. The claim defends a RACE, not an attacker inside the process.

**R5. THE GUARANTEE IS ROUTE-SCOPED: it is the install callback's, and a live token does not imply a claim.** *(Added at v1.1.0 by the security lens's F1, which is the finding this record most needed.)* `introduceTokenVersion` writes a `connector_token_version` and nothing else — no claim, no one-shop check — and 053 §5.3 deliberately allows `install_state_id` to be NULL, because the pilot's Dev Dashboard token is introduced by an operator with no OAuth grant behind it. **So two shops can still end up holding one store with no race at all**: shop A installs store X through the callback and claims it; somebody introduces a token for shop B at store X directly; both are live, and an `app/uninstalled` for X then ends both (053 §7.3) — which is the failure the one-shop rule exists to prevent, reached by a path the rule never sees.

**What was done about it, and what was NOT.** The function is **un-exported from the connector's public barrel** on `claimStoreDomain`'s own precedent, so a caller in `src/` cannot reach it without naming the module — a barrier against a casual caller and explicitly **not** a claim that it is unreachable (the tests import the deep path, deliberately). `completeInstall` is its only production caller today. **What is not done** is making the claim a property of the TABLE rather than of the route — a trigger, or a `shop_domain` foreign key into the claim — which is a schema decision this bead did not open and would need its own record. Until then the honest sentence is the heading: **the install callback guarantees one shop per store; the schema does not.**

## 11. Alternatives considered

1. **Move the F8 check inside the transaction.** Rejected by 056 R10 before this bead: it would fail OPEN under the tenant context (056 §6.1). Not reopened.
2. **Widen `service_write` to `connector_token_version` and run the install in the inbound scope.** Rejected by 056 R10: widening a write policy to close a race is the security lens's F1. Not reopened.
3. **A new `connector_store_claim` table with its own lifecycle.** Rejected: it would need a migration, an append-only decision, a liveness predicate and a second place the one-shop rule lives — to obtain a guarantee the existing index already gives. 041 §4.2(i)'s preference order says use the constraint that exists.
4. **Release the claim on uninstall, in a second transaction after the receipt commits.** Rejected on both mechanism and merit — §4.
5. **Delete the F8 fast path now that the claim guarantees the rule.** Rejected: it would move every refusal past the token exchange and spend the merchant's authorization code to learn something obtainable for free (§3.5).
6. **Refuse rather than re-point a shop that installs a different store.** Rejected: the owner asked for the new store at mint time, and refusing strands a shop on a store it no longer sells into (§3.4).

## 12. Consequences

- The one-shop rule is enforced by the database rather than by a read, so it holds under concurrency without an isolation-level assumption.
- `shop.shopify_domain` acquires its first non-CLI writer, which makes 056 §6.3's oracle reachable and bounded rather than latent (§6) — and makes the draft consumer's store domain the store the grant names (§3.4).
- 042 §5.3(b)'s order grows to six positions, with no handler taking two of them yet.
- One test changed its assertion rather than its subject: the finding-1 regression now proves independence on a shop with no claim, instead of asserting a NULL this bead makes false.
