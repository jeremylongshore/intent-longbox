## 3. The decisions

### 3.1 The self-service MARKER is not a permission, and a permission would be a category error

> **`requires: "self_service"` is a route's declaration that the caller's OWN person is the whole of the authority. It is not a member of `PERMISSIONS`, no role holds it, and `authorize()` never answers it.**

054's eleven permissions are answers to one question: *may this ROLE act on this SHOP's things.* Every one carries a `scope` of `shop` or `location`; every one is decided against a MEMBERSHIP; `authorize()` reads the grants a person holds **at one shop**.

**A password and a second factor are not one shop's things.** `user_credential` and `user_authenticator` carry no `shop_id` at all and are declared row-level-security exemptions for exactly that reason (056 §11 R9, 057 §9 R7): a person may hold memberships at several shops (034 §2.6) and has ONE password across all of them.

**So a permission keyed on a membership would answer per shop.** The same row would be changeable from one counter and not from another, and the first shop whose role did not carry the grant would make a person unable to change a password that is not that shop's to withhold. That is not a strict rule producing a safe answer; it is a rule about the wrong object.

**The marker says the true thing instead**, and it is still a DECLARATION rather than an absence: a privileged route that names neither a permission nor the marker is REFUSED (§3.2), so the class is entered by writing a word with a reason beside it.

**The class is closed by ARGUMENT as well as by type**, and the test enumerates it: a route joins only when every row it reads or writes is keyed on the caller's own `app_user_id`. Five members today — the sign-out, and this bead's four.

⚠ **WHERE EACH MEMBER'S AUTHORITY IS ACTUALLY ENFORCED, because the code's own header said something false about the first one** (the invariant review's delta 6). For the three PRIVILEGED members the marker IS the enforced authority: `enforcePrivileged` refuses a privileged route declaring neither a permission nor the marker. For `POST /api/v1/credentials` the enforced authority is `principal: "device+operator"` on the auth allowlist, checked in `registerAuthentication`; the marker there is a DECLARATION, bounded by `tests/contract/permission-enforcement.test.ts` — and, since R-A, it is what makes the hook write that route's decision row. The two are different guarantees (which COOKIE the hook consults, and which VALUE the table carries) and the record now says which is which.

### 3.2 It REPLACES 057 §4.4's allowlist flag, and 057's own sentence about credentials is narrowed

057 §4.4 built the exception as `AuthAllowlistRow.selfService: true`, for a reason this record agrees with: the route table's `requires` held permissions only, so a route needing none could say nothing at all — and 041 §9.2 item 4 makes an absence indistinguishable from an oversight.

**It is replaced rather than extended because a second member showed what the flag cost.** With it, a privileged route's authority was `ROUTES.requires` **unless** `AUTH_ALLOWLIST.selfService` said otherwise: two tables, two files, and a reviewer had to read both to learn what one route required. The marker is a VALUE in the column every route already fills in — one place to read, one place to get wrong.

⚠ **AND 057 §4.4 SAYS SOMETHING THIS BEAD MUST ANSWER RATHER THAN STEP AROUND.** Its words:

> *A route that touches anything beyond the caller's own session — a membership, a device, a credential, a shop's configuration — is not self-service however it is spelled, and the permission it needs is a decision for 054's matrix.*

**That sentence is NARROWED, and the narrowing is argued rather than asserted.** Its list is a list of things that belong to a SHOP or to a THIRD PARTY: a membership is a shop's grant, a device is a shop's phone, a shop's configuration is the shop's. **A credential is the only entry that is not** — it is the caller's own, tenant-free, and shared across every shop they work at. The ground the sentence gives is right and reaches further than "the caller's own SESSION": the class is *the caller's own PERSON*. So the amendment to 057 reads: **a route that touches anything beyond the caller's own person is not self-service; a route whose every row is keyed on the caller's own `app_user_id` is.** A membership, a device and a shop's configuration stay outside it exactly as before.

**The refusal for a mis-declaration is fail-closed in TWO places.** The privileged branch refuses a route with no authority; and `enforcePermission` — reached only for a tenant-prefixed route with a resolved role at a shop — refuses the MARKER, because a shop-scoped route claiming self-service is claiming that a shop's things are the caller's own.

### 3.3 The FIRST password is set from the operator session, and the DATABASE is what stops it replacing one

> **`POST /api/v1/credentials` requires a `device+operator` session and provisions with `INSERT … ON CONFLICT (app_user_id) DO NOTHING RETURNING id`, falling back — only when that returns no row — to `UPDATE … WHERE app_user_id = $1 AND password_hash IS NULL RETURNING id`, so a CLEARED row is treated as absent (§3.8 property 2) and a LIVE one is refused `409 CREDENTIAL_ALREADY_SET`. `POST /api/v1/credentials/rotations` requires a privileged session AND a fresh second-factor code, and replaces with `UPDATE … WHERE app_user_id RETURNING id`, so it can never create one.**

**The principal is FORCED rather than chosen.** A privileged principal is unavailable by construction — that session is what a password is FOR — and a `device` session alone names no person. The only principal that identifies a human before a password exists is the operator session: the PIN, on a phone the shop enrolled, which 048 §3.5 calls a knowledge factor on a possession-bound channel.

**What that principal is worth is stated rather than assumed.** 048 §3.5's RULE is that an operator session is an attribution of record and is **NOT non-repudiable**: a coworker who watches a PIN can act as that person on that phone. Two consequences follow and both are designed for:

1. **The route provisions and never replaces.** A route that could overwrite a live password would let that coworker lock an owner out of the privileged surface — the owner would hold a password that no longer verifies and no way to reach the rotation route, which needs a session that password opens. Refusing an existing credential removes that act entirely.
2. **The password it sets opens nothing on its own.** `openPrivilegedSession` requires a second factor, and this route mints none. A coworker who sets a password for somebody with no authenticator holds half of a pair for a session neither of them can open.

⚠ **AND THE ROW COUNT IS WHAT ENFORCES (1), WHICH v1.0.0 GOT WRONG** (the data-model lens's H4). That version had ONE `setPassword` upsert — `ON CONFLICT … DO UPDATE`, willing to overwrite — shared by both routes and distinguished only by an `if (existing) throw` in one of them. So the record's central security claim was *"a fact about which of two call sites a future author remembers to invoke"*, and the lens named the third call site that would have inherited the gap silently: the break-glass administration path already on this epic's roadmap, which §3.8 then built. The two statements are now separate primitives whose **return value is the enforcement**, which is 048 R19's own idiom one factor down: *the database decides, not the application.*

⚠ **AND v1.1.1 ADDS A SECOND STATEMENT TO THE PROVISIONING SIDE WITHOUT WEAKENING (1).** §3.8's clearance NULLs the hash, and keying on the ROW made a cleared person unreachable by every surface — so `provisionPassword` now falls back to `UPDATE … WHERE app_user_id = $1 AND password_hash IS NULL RETURNING id` when the INSERT's conflict returns nothing. The predicate is what keeps the claim: **a live hash matches neither statement**, so the coworker of (1) still cannot overwrite one, and the only rows the second statement can touch are ones a schema-owner act deliberately emptied and recorded. `replacePassword` is still the sole path over a live hash.

**409 and not 403, and separate from `CREDENTIAL_REFUSED`.** The caller is not forbidden and the value they chose is not wrong: the world is not in the state the act assumes, and 042 §4.3 requires a client to be able to choose the recovery from the CODE. **The disclosure is stated rather than glossed**: the refusal tells the caller that the person whose operator session they hold already has a password. That is a fact about the identity they just authenticated as, and the alternative — a `201` that wrote nothing — is a screen that lies.

**No ROLE check, and the absence is a decision** (see §6 A4). A password for a person whose only role is `operator` is INERT: the sign-in refuses a person with no MFA-required role and records `role_not_privileged`. Gating the SET route on a membership would make a person-scoped row answer differently per shop, which is the category error §3.1 exists to refuse, and would strand a promoted manager who is no longer at a counter.

⚠ **AND "INERT" IS A PROPERTY OF THE CURRENT ROLE, NOT OF THE PASSWORD** (the security lens's F4). The day an operator is promoted to manager, the password sitting in their row becomes live — including one a coworker set for them months earlier, which nobody has thought about since. That is the sharpest form of §5 R2 and it is why the remedy in §3.8 exists rather than being deferred: a promotion is exactly the moment a squatted credential stops being harmless, and it arrives with no signal.

**The REPLACEMENT re-presents the second factor, and the rule generalises 057 §4.4b rather than copying it.** That section put a fresh code on `role: "owner"` invitations because *the damage OUTLIVES the session it was done from*, and 048 §4.1's freshness window (which 057 §4.3 makes the chain's absolute expiry) bounds sessions rather than acts. **A replaced password is such an act**: the person it locks out cannot sign in again at all, and no expiry undoes that. So the class is now three acts — naming a second owner, replacing a password, replacing a live authenticator — and `FRESH_SECOND_FACTOR_REQUIRED`'s registry entry names the RULE rather than the first act that met it.

**There is no `current_password` field.** The session was established with the password inside the freshness window, so asking again re-tests a factor the session already carries. What the request re-presents is the factor the session carries no fresh proof of.

### 3.4 An enrolment is TWO requests, the unconfirmed secret is SEALED in the CLIENT, and the ticket is SPENT by the database

> **`POST /api/v1/authenticators/offers` mints a secret, seals it into a ticket bound to the person and the expiry, and returns both the `otpauth://` URI and the ticket. `POST /api/v1/authenticators` takes the ticket back with a code generated from the secret inside it — and INSERTs `authenticator_offer_use (ticket_digest)` in the same transaction, so a ticket is confirmed exactly once.**

048 §4.3 rules that **a secret that is never confirmed never becomes a row**. `pnpm enroll-authenticator` satisfies that by holding the secret in MEMORY across one operator's decision — honest for a terminal, and unavailable to a request/response surface where the two halves are two requests that may not even reach the same process.

**Three answers were on the table and two are worse** (§6 A1–A3). A row for the unconfirmed secret stores the exact object §4.3's sentence keeps out of the database; a map in this process works on one instance and silently stops working on two; a client-chosen secret means the server accepts key material from a body and can say nothing about its entropy.

**So the ticket is `seal(ring, secret, aad)` — 048 R18's own envelope, reused rather than re-derived**, so there is no second cryptographic construction in this system to review. The AAD is `authenticator-offer:v1:<app_user_id>:<expires_at_ms>` and every field is load-bearing:

- **the person**, so a lifted ticket fails: the confirming call names no person at all — it takes one from the SESSION — and a ticket minted for somebody else does not authenticate under it;
- **the expiry**, so the lifetime is INSIDE the authenticated bytes; a client that edits the wire's `expires_at` changes nothing;
- **a version tag**, so a later shape is a different AAD rather than an ambiguity.

⚠ **A TICKET IS SINGLE-USE, AND v1.0.0 SAID THE OPPOSITE** (the security lens's F2). That version wrote: *"a ticket is NOT single-use and is NOT a credential — confirming one twice enrols twice, and the second enrolment supersedes the first exactly as any re-enrolment does."* The lens replayed one forty seconds after its first confirmation, under a NEW `Idempotency-Key`, and got a second `201`: a second authenticator, and eight FRESH recovery codes, which **silently retired the set the person had just written off the screen** — for the person in 048 §8.1's re-enrolment state, the set they need most. "Supersedes exactly as any re-enrolment does" is precisely the wrong property for an artifact nobody re-presented on purpose.

So the ticket joins 048 R15's idiom, which this schema already uses three times (`invitation_use`, `device_enrollment_code_use`, `recovery_code_use`): **single use is a CONSTRAINT or it is a race.** The key is the ticket's DIGEST, because a sealed value has no row of its own to point at — that being the point of sealing it — and the digest is already computed for the idempotency hash. **A genuine RETRY is unaffected**: `replayIfSettled` answers it before the transaction opens, so what the constraint bites is a RE-SUBMISSION under a new key, which is a second act.

**A person who still HOLDS a live factor must present a fresh code from it; a person in 048 §8.1's re-enrolment state must not.** The branch is on `mfaState` and never on a field the caller supplies, so a caller cannot choose which rule applies to them by omitting one. The two codes in the request are from two different secrets and conflating them would be a hole: `code` proves the new secret, `fresh_totp_code` proves the old.

**The idempotency body hash is the TICKET'S DIGEST and never the confirming code**, and the version that was not is the one defect CI caught here (§0). A TOTP code changes every thirty seconds for one logical enrolment, so hashing it made a retry after a lost response a `422` — the very failure 042 §5.1 describes, arriving through the mechanism meant to prevent it. §3.9's declaration is what now makes that choice visible to a reviewer rather than buried in a comment.

**The recovery set is spliced onto the RESPONSE and never onto the stored body** — 057 §4.8 verbatim, one credential up. A replay after a lost response returns a truthful `201` with the enrolment's id and no codes, and the person enrols again, which supersedes the set they did not see. **The security lens probed this rather than reading it** (F8): the redaction happens BEFORE storage, not at replay, so a dump of `request_idempotency` contains no code — `LEAK HITS []` — which is a stronger property than "a replay does not return them" and is the one I7 asserts.

### 3.5 048 §8.1's *"nothing else"* becomes a DECLARED set

> **`RouteSpec.reachableWhileReenrolling` names the routes a `must_reenroll` session may reach. Three members: the sign-out and the two halves of an enrolment. Everything else refuses `MFA_REENROLLMENT_REQUIRED`.**

E03-D11 enforced §8.1 with `ctx.spec?.requires !== null` — which meant *"everything except the sign-out, because the sign-out is the only route that declares nothing."* That was a PROXY for a one-member set, and it stops being true twice in this bead: the enrolment routes must be IN the set, and the sign-out no longer declares nothing.

A route added later is OUTSIDE the set by default, which is the direction §8.1 asks for.

**The password routes are outside it, and the ground is 048 §8.1's own text rather than a threat argument.** *(v1.0.0 argued that a recovery-code session is the one an attacker holding a slip of paper would hold — which the invariant review's delta 5 correctly points out cuts just as hard against the two enrolment routes that ARE in the set, and therefore decides nothing.)* The load-bearing reason is what the state is FOR: §8.1 says such a session *"can reach NOTHING else until"* the person has re-enrolled, and the set is exactly the acts that END the state plus the one act that always remains available (signing out). A password is not one of them, so it is not in the set.

**The gate still lifts BY PREDICATE.** `mfaState` reads *"no live authenticator, and a recovery-code use exists"*; enrolling makes the first half false. Nothing sets a flag, nothing can be left stale, and I5 proves it with the SAME cookie across the gate.

### 3.6 The credential surface gets its OWN budget, keyed on the SESSION CHAIN

> **`PROVISIONAL_CREDENTIAL_WRITE_RATE_PER_SESSION` (5/min), its own map, taken in the service on `session.chain_id`, BEFORE any hashing.**

Inheriting the shop's `ordinary` rate would repeat 057 §4.5a's F2/F3 in a new place: 120/min is a phone working through a box of books, nobody sets twelve passwords a minute, and a shared map means a loop on a credential route spends the budget the counter needs.

**Keyed on the CHAIN, and that is deliberate rather than convenient.** 048 R14 forbids keying on a PERSON, and its ground is *"a stranger must not be able to exhaust a named person's budget"* — a rule about routes a stranger can reach. Every route this bucket covers requires a live session, so only its holder can spend it. It is not 019 T35's forbidden per-operator surface either: the key is a session, and the count is never rendered, grouped, exported or joined to anybody.

⚠ **AND THE BOUND IS COMPOSITE, WHICH IS THE HALF A READER WOULD OTHERWISE HAVE TO WORK OUT** (the security lens's F5). Keying on a chain would be weak if a fresh chain were free. It is not, and the cost differs by principal: a new PRIVILEGED chain costs a full sign-in — bounded by `PROVISIONAL_SIGN_IN_RATE_PER_IDENTIFIER` at 5/min per submitted identifier AND by an unspent TOTP step, which 048 R19 makes one per thirty seconds — so roughly one new chain per half-minute, not per request. A new OPERATOR chain costs a PIN on an enrolled phone, under 048 §9.1's growing per-pair lockout. Neither number is a measurement and neither is quoted as one (021 B16); what the composition says is that the per-chain bucket is not trivially resettable, which is the property it needs.

**Two buckets, two questions**, which is the split three other routes already make: the route's DECLARED class is taken by the hook (the device bucket for the operator route, the shop's ordinary bucket for the three privileged ones), and this one answers what those cannot.

### 3.7 A self-service act IS recorded, under a marker that names no grant — on BOTH branches

> **A MUTATING self-service route writes one `authorization_decision` row: `permission = 'self_service'`, `membership_id` NULL, `role` NULL, `decision = 'allowed'`, with the matrix version and the session chain. The hook writes it from the PRIVILEGED branch and from the OPERATOR branch, the second of which is outside the tenant-prefix guard.**

054 §4.3 records *every refusal, plus an allowance where the act MUTATES or the permission is PRIVILEGED*. There are no refusals to record in this class — the caller's own identity is the whole of the authority, so there is no decision to lose — and what is left is the allowance. **Setting your own password and replacing your own second factor are the strongest things a session can do to the identity it holds**, so they are recorded on the same terms as an invitation.

⚠ **AT v1.0.0 THE ONE ROUTE THIS BEAD EXISTS FOR RECORDED NOTHING, AND THE RECORD CLAIMED OTHERWISE** (the security lens's F1, the invariant review's BLOCK, the gate audit's B1). `recordSelfServiceDecision` was reached only from the privileged branch; the operator branch's audit call sits inside `if (url.startsWith(TENANT_PREFIX))` and `POST /api/v1/credentials` is deliberately outside the prefix (§3.1). So the act performed by the one principal 048 §3.5 calls not non-repudiable was the only one in the class with no trail — and I9 evidenced the claim on a privileged sibling, which is exactly the shape 061 §0 warns about: a test that passes for a route other than the one the sentence is about. The hook now records from both branches, and I9 asserts the row for `/credentials` by name.

**The marker in the `permission` column is the point.** `self_service` is deliberately absent from `PERMISSIONS`, so an auditor who looks it up finds nothing — which is the true statement: *no grant decided this act*. `membership_id` and `role` are NULL for the same reason, and `migrations/028`'s CHECK permits that pair. `matrix_version` is still stamped because it records which build's rules were in force, which stays answerable after the constant moves.

⚠ **AND A SELF-SERVICE ALLOWANCE IS AN ALLOWANCE TO *ATTEMPT*.** The hook runs before the handler, so a `201` and a `409 CREDENTIAL_ALREADY_SET` both record `allowed` — the act was permitted; whether the world was in the state it assumed is a different question, answered by the effect. That is 059's N:1 ruling arriving one class over, and it is stated here rather than fixed: **there is deliberately no outcome column**, because a column the hook cannot fill truthfully would be worse than an absence a reader can see, and an auditor who needs the outcome has the credential row and the clearance table. I9 asserts the second row rather than leaving somebody to find it in a query.

**It does not create a new per-person surface** (022 P3): the row names the route TEMPLATE, the shop and the chain, never the person — and `session_chain_id` stays UNINDEXED, so the join that reconstructs a shift still costs a sequential scan.

### 3.8 A clearance is an UPDATE plus a FACT, and never a DELETE

> **`pnpm clear-credential --user <uuid> --reason squatted_credential|lost_credential` NULLs `user_credential.password_hash` and appends a `user_credential_clearance` row naming the reason. It runs as the SCHEMA OWNER and is break-glass.**

⚠ **THIS EXISTS BECAUSE THE SECURITY LENS WENT LOOKING FOR THE REMEDY §5 R2 PROMISED AND FOUND NOTHING** (F3, the gate audit's B2). R2 accepted a real residual — a coworker who watches a PIN can set a FIRST password for somebody who has none — *"and the owner's remedy is to discover it and ask for the row to be cleared"*. There was no clearing at any level: `migrations/031`'s `ENABLE ALWAYS` trigger refuses a DELETE on `user_credential` to EVERYONE including the schema owner, and no route and no script cleared one. **A watched PIN was a permanent lockout of the privileged surface, remediable only by disabling a trigger by hand** — and §3.3's F4 note is what makes that sharp rather than theoretical, because a promotion turns an inert squatted password into a live one with no signal.

**The trigger stays exactly as it is, and so does the row.** `user_credential` is 048 §9.1's LOCKOUT ANCHOR for the first factor: a row that could be deleted is a lockout that could be reset by deleting it, and the failure history the delay is derived from would go with it. So the clearance sets `password_hash` to NULL — inside `031`'s own three-column licence, which is why no migration touches that trigger — and the FACT is a row in `user_credential_clearance` (`migrations/037`), naming the reason, the person who did it and a free-text note.

**Three properties follow, and each is tested** (I14):

1. **A NULL digest verifies against nothing.** `verifyPassword` pays the decoy's cost and answers 048 §9.3's constant refusal, exactly as it does for a person who never had a credential — the branch it already had.
2. ⚠ **A CLEARED ROW IS ABSENT FOR PROVISIONING PURPOSES, AND v1.1.0 SAID THE OPPOSITE.** That version had this property read *"the counter-phone route stays REFUSED, because `provisionPassword`'s `ON CONFLICT (app_user_id) DO NOTHING` keys on the ROW and the row is still there"*, and the code agreed with it — so after a clearance the route answered `409`, the CLI's own closing message promised a path that did not exist, and `--reason lost_credential` had no outcome at all. **A cleared person was unreachable by every surface**, which made the remedy a better lockout than the squat it was built to undo; the invariant re-verification blocked on it and the acting head ruled that **the CODE changes, not the message**. `provisionPassword` INSERTs `ON CONFLICT DO NOTHING RETURNING id`, and when that returns no row it REVIVES — `UPDATE user_credential SET password_hash = $2 … WHERE app_user_id = $1 AND password_hash IS NULL RETURNING id` — inside `031`'s own licence, which is a negative check on four IMMUTABLE columns (`id`, `app_user_id`, `created_at`, `authored_by`) and says nothing about the value of the hash, so no migration touches that trigger either. **The affected-row count is still the authorization**: a live hash matches neither statement and still refuses `already_set`, and `replacePassword` behind a fresh second factor stays the only path that overwrites one. **A clearance is a TERMINAL act; the person is then provisioned from the counter phone by the ordinary first-password route, which treats a cleared row as absent.** What it does not do is undo the squat's exposure — §5 R2 keeps that residual.
3. **The fact is append-only** and the app role holds NO privilege on it (`appGrant: "none"`), on `app_user_origin`'s reasoning (058 §5): a table recording an intervention must not be writable — or readable — by the process the intervention is about.

**`--by` is an accountability record that nothing verifies** (058 R1's shape); what substitutes is that running this needs the schema owner's database URL and shell access. **It writes no `authorization_decision` row**, and the reason is mechanical rather than a preference — see §8, where the decline is recorded.

**This is not the route.** A support-facing clearance with a session behind it is **E11-B09**'s, which owes break-glass administration a surface.

### 3.9 Two declarations that turn comments into checks

**`RouteSpec.idempotencyHashOf`** (the data-model lens's H5). Five routes hash something other than their literal body, each for a good reason — a password and an invitation code are low-entropy secrets a stored SHA-256 would be an offline verifier for (048 §9.2); an address is a person; a confirming code is a TOTP value that changes every thirty seconds. Until now every one of those reasons lived in a comment. 042 §5.1 class TWO already solved the same problem one class over — a member NAMES its constraint and a test reads the migrations to confirm it exists — so the same shape applies: the route declares in plain English what its hash is taken over, and `tests/contract/idempotency-hash-declaration.test.ts` asserts the SERVICE builds that shape and that no builder puts a raw secret in the hashed body. **The failure it would have caught is §0's, and it is not hypothetical.**

**`pnpm arch`'s `break-glass-scripts-are-unreachable`** (H6). Three scripts — `enroll-authenticator`, `redeem-recovery-code`, `clear-credential` — carry headers saying they are break-glass, and the property those headers describe is mechanical: *no served code path can reach this*. A header is a sentence a reviewer is trusted to keep noticing; the rule is an assertion over the whole SERVER TREE (not just `src/routes/` — a service imported by a route is as reachable as the route). The day somebody imports one "to reuse the logic", the substitution that stands in for a password — 048 R20's first half, unenforceable from a shell tool — silently becomes reachable over HTTP.

## 6. Alternatives considered

**A1 — A row for the unconfirmed secret.** *Rejected*; §3.4. It stores a live TOTP secret for somebody who has not proved they hold it — the object 048 §4.3's sentence exists to keep out of the database — and grows a table nobody reaps.
**A2 — A map in this process.** *Rejected*; §3.4. Correct on one instance, silently wrong on two, and a restart mid-enrolment becomes an unexplainable refusal. An authentication flow whose correctness depends on the process count fails the first time somebody scales it.
**A3 — Let the CLIENT choose the secret.** *Rejected*; §3.4. The server would accept key material from a body and could say nothing about its entropy; a buggy client enrolling a constant is invisible until it is a breach.
**A4 — Refuse a first password to a person whose only role is `operator`.** *Rejected*; §3.3. It makes a person-scoped row answer differently per shop, which is §3.1's category error arriving through a side door, and the credential is inert anyway — the sign-in refuses the role. `enrollAuthenticator`'s own role check STAYS, and the asymmetry is argued: a second factor is key material sealed under the ring, not an inert digest.
**A5 — A new permission (`credential.self.manage`) instead of the marker.** *Rejected*; §3.1. A permission is decided against a membership; this act has no membership to decide it, and inventing one would let a shop withhold a person's own password.
**A6 — Keep 057 §4.4's `selfService` flag and add the routes to it.** *Rejected*; §3.2. Two tables for one rule, and the flag's own justification is better served by a value in the column every route fills in.
**A7 — Let the first password be set AT invitation redemption.** *Rejected*. 048 §7.2 defines that act as *"the employee enters it on the enrolled device and sets a PIN"*, and a redemption is single-use under `UNIQUE (invitation_id)`: a password refused for length inside it would either roll back the whole redemption (spending the invitation for nothing) or need a second write path. A separate route keeps the redemption what §7 says it is, and can be reached again after a mistyped password.
**A8 — Allow a `must_reenroll` session to change its password.** *Rejected*; §3.5, on 048 §8.1's own text: the set is the acts that END the state, plus signing out.
**A9 — One route for the offer and the confirmation, branching on the body.** *Rejected*; §3.4. A route whose response TYPE depends on which fields the caller sent is a route no generated artifact can describe honestly (042 §3.3 property 3).
**A10 — Ask for the current password on the rotation route.** *Rejected*; §3.3. The session was established with it inside the freshness window; re-testing it adds a second thing to get wrong and defends nothing the session does not already prove.
**A11 — DELETE the credential row to clear it.** *Rejected*; §3.8. The row is 048 §9.1's lockout anchor and `migrations/031`'s trigger refuses a DELETE to everyone including the schema owner — deliberately, because a row that could be deleted is a lockout that could be reset by deleting it. NULLing the hash inside that trigger's own licence keeps the anchor and its history.
**A12 — A second `principal`-like column instead of the marker** — i.e. express "no grant decides this" as a property of the principal rather than of the authority. *Rejected*, and the data-model lens agreed unprompted (§2.2): the marker answers *whose grant decided this* and a principal answers *what did the caller present*, which are different questions with different answers on the same route.
**A13 — Make the clearance a route now.** *Rejected*; §3.8, §5 R2. A clearance acts on ANOTHER person's credential, so it is not self-service under §3.1's own test and would need a permission, a session shape and a disclosure rule this bead has not argued. E11-B09 owns break-glass administration.
**A14 — Add an eviction of other privileged chains on password rotation.** *Rejected*; §5 R8. 057 §4.4a already gives the mechanism, and a second trigger for the same rule is a second place for it to be got wrong.

## 8. Positions adopted differently, and the one item DECLINED

Recorded per 054 §14's and 061 §2's idiom: a ruling followed in a shape its author did not ask for, or not followed at all, is a decision a reviewer must be able to see.

**DECLINED — an `authorization_decision` row for the credential clearance.** The ruling asked for one beside the clearance fact. It is not written, and the ground is mechanical rather than a preference: **`authorization_decision.shop_id` is `NOT NULL REFERENCES shop(id)`**, and a credential clearance has no shop — the credential crosses every shop the person works at (§3.1). Writing one would mean either naming a tenant the act does not have (a false row in the one table an auditor trusts about authority) or multiplying one act across every shop the person holds a membership at (N rows for one decision, which 059 §5 refuses in the other direction). `user_credential_clearance` IS the record, and it holds strictly more than a decision row could: the reason, the note, the person who did it and the credential it names. **A schema change to make `shop_id` nullable is a 054 decision this bead has not argued**, and E11-B09 — which owns break-glass administration — is where a break-glass act with a SESSION behind it would raise it properly.

**ADOPTED DIFFERENTLY (1) — H6's scope.** The ruling asked that the break-glass scripts be asserted unreachable *"from nothing under `src/routes/`"*. The rule ships over the whole of `src/`, which is strictly stronger and is the property the header actually claims: a service imported by a route is as reachable as the route, so a rule that watched only the route layer would pass while the import sat one file away.

**ADOPTED DIFFERENTLY (2) — R-C's shape.** The ruling offered "NULL hash **or** a retirement FACT row" and steered toward both. Both ship, and the record states why they are not redundant: the NULL is what makes the credential stop verifying, and the fact is what makes the act answerable — neither substitutes for the other, and the row deliberately does **not** carry the old digest.

Measured on THIS branch before the rebase, the newest fixture is `after-033` (32 applied, because `027` is a gap) and head is 35 files with this bead's `037`, so the distance is **3** and no fixture is owed. **E03-D21 lands `036` AND a new `after-035.sql` fixture**, so after the rebase the distance is smaller still and the answer does not change.
